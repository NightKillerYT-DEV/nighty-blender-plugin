# Nighty Blender: how the parts talk (protocol v2)

Two parts on the person's computer: the **Nighty Blender plugin** inside Nighty Vault, and the **Blender add-on**.
Nothing is hosted anywhere; GitHub releases only hold the files. Nighty Blender has no AI model and never generates
one: models come from the person's file, an import, or code only when the person asks.

```
AI app --stdio MCP--> nighty-vault.exe --mcp --(127.0.0.1 + token)--> Nighty Vault app
        --> plugin/main.js (nighty.mcp.onCall: the 15 blender_* tools)
        --WebSocket ws://127.0.0.1:47871 (47872, 47873), subprotocol nighty-blender.v2-->
        Blender add-on "Nighty Blender" (Python extension, GPL) --> bpy on Blender's main thread
```

v1 (the Node program `nighty-blender-mcp.mjs` that listened, with the add-on as the client) is retired. In v2 the
**add-on listens** and the plugin connects.

## 1. The plugin side (Nighty Vault)

- `plugin/plugin.json` declares `permissions: ["system", "panel", "storage"]` and the `mcp` field (prefix `blender`,
  the note, the 15 tools), generated by `scripts/gen_plugin_json.py` from `addon/nighty_blender/tools.json`. Nighty
  Vault shows every tool on the install screen; a changed tool list or note asks the person again. The contract is
  `PLUGIN-MCP-CONTRACT.md` (shared with the Nighty Vault core) and Nighty Vault's docs/PLUGINS.md.
- `nighty.mcp.onCall(tool, args, ctx)` forwards every tool as a `call` (below), except `job { action: "wait" }`,
  which the plugin answers itself from the `job` messages it has seen: at most 45 s per call (Nighty Vault gives a
  call 58 s; the plugin gives Blender 55 s). Results stay under 8 MB (pictures are dropped first, with a note).
- Without a paired, connected Blender every tool but `status` answers isError with what to do.

## 2. The connection

- The add-on listens on the first free port of 127.0.0.1:47871-47873 (Nighty Design uses 47823-47825: never those).
  On Windows the socket is exclusive (`SO_EXCLUSIVEADDRUSE`), so no other program can share the port. Tests use
  `NIGHTY_BLENDER_PORTS=0` (any free port).
- The upgrade request is refused (HTTP 403 / 400, then closed) unless: it is a WebSocket upgrade (version 13, a key),
  `Host` is `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding), there is no `Origin` header or it is `null`
  (the plugin's worker has an opaque origin; web pages always send their own), and the subprotocol list has
  `nighty-blender.v2`. The answer names that subprotocol.
- Frames: client frames must be masked; JSON text messages only (binary closes); a message over 16 MB (after
  reassembly) closes the connection; pings are answered. At most 4 connections; one that never pairs is closed
  after 10 minutes.
- Closing is graceful (close frame, then the socket a second later), so the last message is never lost to a reset.

## 3. Pairing and authentication (nothing works before it)

Every message has `type`. Before pairing, only `hello`, `ping`, `auth`, `pair_request`, `pair_fail` and
`pair_confirm` are answered; anything else gets `error { code: "unpaired" }` (a `call` gets a `result` with isError).

1. Plugin -> `hello { v: 2, nonce: 32 hex, client: { name, version } }`.
   Add-on -> `hello { v: 2, addon, blender, python, nonce: 32 hex, paired, locked, level, kdf: { name:
   "pbkdf2-sha256", iterations: 100000 }, proof? }`. `proof` is there when the add-on keeps a pairing.
2. **Reconnect (the plugin keeps a token):** the plugin first checks Blender's proof,
   `HMAC-SHA256(token, "nb2/server-auth|" + nonce_c + "|" + nonce_s)` (the token's 16 bytes are the key). Wrong or
   missing: this listener is not the Blender it paired with (a fake listener, or another Blender): the plugin sends
   nothing more and tells the person. Right: it sends `auth { proof: HMAC(token, "nb2/client-auth|" + nonce_s + "|"
   + nonce_c) }`; the add-on answers `ready` or `error { code: "auth_failed" }` and closes.
3. **First pairing:** the person presses Pair in the plugin's Night Panel card. The plugin makes a random 6-digit
   code (uniform), shows it, and sends `pair_request`. The add-on answers `pair_wait` and its N panel (Nighty tab)
   asks for the code. Two programs asking at once both get `error { code: "busy" }` (nobody is paired).
   The person types the code in Blender. Both sides derive
   `key = PBKDF2-HMAC-SHA256(code, "nighty-blender.v2|" + nonce_c + "|" + nonce_s, 100000, 32 bytes)`.
   - Blender proves first: `pair_proof { proof: HMAC(key, "nb2/server-pair|" + nonce_c + "|" + nonce_s) }`.
   - The plugin checks it with its own code. Wrong: `pair_fail` (the person typed a different code). Right:
     `pair_confirm { proof: HMAC(key, "nb2/client-pair|" + nonce_s + "|" + nonce_c) }`.
   - The add-on checks that, makes a random 16-byte token and answers `paired { box }` with
     `box = token XOR HMAC(key, "nb2/token-box|" + nonce_c + "|" + nonce_s)[0:16]` (hex), then `ready`.
   - Each wrong code (a `pair_fail`, or a wrong `pair_confirm`) counts. After **5 wrong codes pairing is locked**
     (`error { code: "locked" }`) until the person presses Unlock in Blender's panel. A request waits 5 minutes for
     the code (`error { code: "pair_timeout" }`).
4. `ready { addon, blender, level, file, tools }`: calls work now. One proven connection at a time: a newer one
   replaces the older (`bye { reason: "replaced" }`; the plugin then waits for the person instead of fighting).

Where the token lives: the plugin keeps it in its own data folder outside the vault (`<dataDir>/pairing.json`; the
vault may sync); the add-on keeps it in its extension user folder (`pairing.json`, `NIGHTY_BLENDER_STATE_DIR` in
tests). Never in a .blend, a vault page or the AI's context. `forget` (either side) deletes it; the other side gets
`bye { reason: "unpaired" }`.

What this does and doesn't protect: a web page can't connect (Origin, Host), nothing runs before pairing, a listener
that never saw the code or the token can't pass the plugin's check, and guessing online is capped at 5. The code is
6 digits, so a program already running on the same computer that relays both sides while the person pairs could try
the codes offline (PBKDF2 makes each try cost 100,000 rounds); such a program could also read the token files. The
person sees the pairing in both apps and can Forget it at any time.

## 4. After pairing

- Plugin -> `call { id, tool, args, client, sessionId }`; add-on -> `result { id, content: [text / image blocks],
  isError }`. Calls run one at a time on Blender's main thread.
- Slow tools answer at once with `{ "job": "<id>" }` (as the result's JSON text); the add-on then sends
  `job { id, job: { id, tool, state: running | done | failed | cancelled, progress 0..1, message, result? } }`
  as it goes. `blender_job` wait / cancel / get / list.
- `info { level, file }` when the person changes the safety level; `config { instantMeshes: path }` (plugin -> add-on,
  the Instant Meshes program the plugin installed; `config_ok`); `forget`; `ping` / `pong`; `bye`.

## 5. Tools

- The single source is the registry in `addon/nighty_blender/tools/`: working steps register with `@action`
  (cleanup_mesh, retopo, bake, export_asset...), and the 15 public tools with `@tool` in `tools/public.py`:
  `status`, `scene`, `look`, `measure`, `check`, `reference`, `import`, `mesh`, `texture`, `make_game_ready`,
  `export`, `run_python`, `undo`, `job`, `guide`. Routers (`mesh`, `texture`, `check`) take `op` / `what`; their
  schemas are built from the steps' schemas. `tools.json` is generated (`blender -b --factory-startup --python
  scripts/gen_tools_json.py`), then `plugin/plugin.json` (`python scripts/gen_plugin_json.py`); tests check both.
- Every call that changes the scene is ONE undo step named "AI: <step>"; `undo` takes back only those (and
  checkpoints). `import` keeps a locked `<name>_SOURCE` copy (never changed; `check { what: "source" }` compares).
- Safety levels, set by the person in the N panel only (the panel refuses a change while the AI's code runs):
  tools only / safe Python (bpy, bmesh, mathutils, math, random, nighty; no files, programs, network or imports) /
  full Python.

## 6. Versions and releases

- The add-on's version is `blender_manifest.toml`'s (2.0.0); the plugin's `plugin.json` version is the same.
- A release tag `vX.Y.Z` builds (`scripts/build_release.py`, `.github/workflows/release.yml`): the add-on zip, its
  SHA-256 and size pinned into the plugin's `main.js`, the `.nightyplugin`, `skills.zip`, `SHA256SUMS`, and build
  attestations. The plugin is the only updater of the add-on: it downloads the pinned zip, checks the SHA-256, finds
  Blender 4.2 or newer and runs `blender --command extension install-file -r user_default -e <zip>`, then checks the
  installed version. Fallback: drag the zip into Blender.
- The public repository is https://github.com/NightKillerYT-DEV/nighty-blender-plugin; the plugin's pinned add-on URL
  is `https://github.com/NightKillerYT-DEV/nighty-blender-plugin/releases/download/vX.Y.Z/nighty_blender-X.Y.Z.zip`.
